# 接口设计

当用户想探索某个加深候选项的备选接口时，使用这个并行子代理模式。它基于 Ousterhout 的 “design it twice”：你的第一个设计想法很可能不是最好的。

使用 [LANGUAGE.md](LANGUAGE.md) 中的词汇：**模块**、**接口**、**接缝**、**适配器**、**杠杆**。

## 流程

### 1. 构建问题空间

生成子代理之前，先写一段面向用户的问题空间说明，覆盖所选候选项：

- 任何新接口都必须满足的约束
- 它依赖哪些东西，以及这些依赖属于哪个类别（见 [DEEPENING.md](DEEPENING.md)）
- 一段粗略的说明性代码草图，用来让约束具体化；它不是提案，只是把问题说清楚

把这段说明展示给用户，然后立刻继续第 2 步。用户可以边读边思考，子代理并行工作。

### 2. 生成子代理

使用宿主 agent 可用的委托能力，并行生成 3 个以上子代理。Codex 使用原生子代理；Claude Code 使用 Task/Agent 工具；如果宿主没有委托能力，就自己写出三个清晰分开的设计。每个设计都必须给加深后的模块提出一个**完全不同的**接口。

给每个子代理一份独立技术 brief：文件路径、耦合细节、[DEEPENING.md](DEEPENING.md) 里的依赖类别、接缝背后是什么。这份 brief 独立于第 1 步的用户问题空间说明。给每个代理不同设计约束：

- Agent 1：“最小化接口：目标是 1-3 个入口点。最大化每个入口点的杠杆。”
- Agent 2：“最大化灵活性：支持更多用例和扩展。”
- Agent 3：“优化最常见调用者：让默认路径非常简单。”
- Agent 4（如适用）：“围绕跨接缝依赖的 ports and adapters 设计。”

在 brief 中加入 [LANGUAGE.md](LANGUAGE.md) 词汇和 CONTEXT.md 词汇，确保每个子代理用架构语言和项目领域语言一致地命名。

每个子代理输出：

1. 接口：类型、方法、参数，以及不变量、顺序、错误模式
2. 使用示例：调用者如何使用它
3. 实现背后隐藏了什么
4. 依赖策略和适配器（见 [DEEPENING.md](DEEPENING.md)）
5. 权衡：哪里杠杆高，哪里杠杆低

### 3. 展示和比较

按顺序展示设计，让用户能逐个吸收，然后用 prose 比较。通过**深度**（接口上的杠杆）、**局部性**（变化集中在哪里）和**接缝位置**进行对比。

比较后给出你的建议：你认为哪个设计最强，以及为什么。如果不同设计里的元素可以很好地合并，就建议一个 hybrid。要有判断；用户想要的是强阅读，不是一份菜单。
